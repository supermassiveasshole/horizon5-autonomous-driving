# FH5 歌利亚自动驾驶：可行性评估与实验路线

范围状态更新：Q1–Q15 及自主学习、奖励投机要求已经收敛，当前需求基线见 [PRD v1.0](PRD.md)。用户选择自己的兰博基尼第六元素与固定调校，目标是 RL 实质参与歌利亚全程、先超过个人通常有效表现再挑战最佳，之后探索对手与名次；七天是探索窗口。下文算法、选车、验收与排期保留调研时的候选建议，尤其早期选车与“RL 短段作为进阶”不应覆盖新决定；讨论历史见 [范围记录](scope-decisions.md)。

技术方案更新：依据用户对性能上限、及时里程碑和自主倒带的补充要求，当前主线建议见 [驾驶学习主方案](driving-learning-design.md)。本文件保留方法比较与原始调研，不将早期“仅学习速度/小幅残差”的建议当作最终策略的永久限制。

原始评估日期：2026-09-28。以下保留当时的假设与分析：目标按 Forza Horizon 5 的 The Goliath（歌利亚）理解；允许游戏遥测和预先记录的路线，最初考虑先跑完全程再探索强化学习。当前方案已允许短段学习与基线全程调试并行，实施以 PRD 为准。原始评估未启动游戏、安装控制驱动、训练模型或实测完赛。

## 结论

本机足以支持这个 toy project。最合理的顺序是：**遥测与路线录制 → 保守的闭环路线跟踪 → 强化学习优化速度和控制 → 可选的视觉感知**。首个里程碑是单车、固定调校、明确辅助设置下，连续完成歌利亚；速度优化和泛化另作实验。

这是基于硬件、公开接口和方法性质的工程判断，不是已有 FH5 完赛实测。当前最大不确定性是控制接口、自动重开、检查点判定和持续运行的稳定性，不是神经网络容量。增加 GPU 无法让单个正常运行的游戏实例凭空产生更多游戏时间。

| 工作盘 | G:，NVMe，约 434.4 GiB 可用 | 放环境、数据、模型和缓存 |

建议初测游戏窗口化 / 无边框、1080p 或 720p、限制为 60 FPS；策略先用 20 Hz，保留游戏渲染和训练的余量。此处是起始配置，不是本机基准结果。小型 MLP 可比较 CPU 和 GPU 推理延迟，不必强制占用 GPU。CUDA 驱动信息不等于已验证 PyTorch CUDA 环境。

## 参考项目的价值与迁移边界

[ForzaHorizon6-VisionAI](https://github.com/Ayin1412/ForzaHorizon6-VisionAI) 的主要价值是把道路几何作为感知与控制之间的接口。它采用监督学习 / 行为克隆（BC），不是强化学习训练系统。作者说明没有 RL 微调或 DAgger，录制器也未包含在发布中。[项目说明](https://github.com/Ayin1412/ForzaHorizon6-VisionAI#training)

可借鉴感知和控制分层、动作标定、日志与可视化思路。迁移时须重新验证 FH5 的遥测包、手柄响应、摄像机与路线数据；不能把 FH6 权重在 FH5 的表现当作已验证能力。完整源码核查见 [参考项目审计](reference-project-audit.md)。

它的 camera-only 也不等于零遥测：模型配置仍使用速度、纵向加速度和上一动作状态。项目没有给出可用于本机外推的 GPU 型号、实测延迟或训练耗时；30 Hz 是控制循环设定。[模型配置](https://github.com/Ayin1412/ForzaHorizon6-VisionAI/blob/main/data/models/meta.json)、[驾驶源码](https://github.com/Ayin1412/ForzaHorizon6-VisionAI/blob/main/scripts/drive.py)

## 方案比较

以下优先级是针对用户目标的建议，而非对各算法普遍能力的排名。

| 路线 | 学什么 / 做什么 | 优点 | 主要代价 | 建议 |
|---|---|---|---|---|
| 路线 + 传统反馈控制 | 根据当前位置、朝向、速度跟踪参考线 | 无需训练，便于诊断，形成老师和基线 | 标定、速度规划、复杂路段调参 | 首先完成 |
| 路线 + SAC 学目标速度 | 转向由基线执行，策略选择速度或其修正量 | 动作空间小，能研究提前刹车 | 奖励、探索与训练数据 | 第一项 RL 实验 |
| 路线 + residual SAC | 策略输出基础控制器的有限修正 | 利用先验减少无意义试错 | 状态/动作语义及限幅须一致 | 随后推进 |
| 路线 + 低维 SAC / TD3 全控制 | 策略直接输出转向及加减速 | 较完整的 RL 对照 | 更依赖采样和训练稳定性 | 可选对照 |
| BC 后在线 RL | 从示范初始化策略，再交互优化 | 可复用成功驾驶数据 | BC warm start 和 RL 衔接需实现 | 有示范后考虑 |
| 像素端到端 RL | 同时学视觉、定位和控制 | 研究面广 | 采样、内存、延迟和诊断困难叠加 | 后续独立阶段 |
| 学动力学模型 / 世界模型 | 在预测模型里规划或训练 | 可能减少游戏交互 | 模型误差与游戏迁移本身成为新课题 | 假期首版不优先 |

SAC 支持连续动作和经验回放；PPO 也可用，但单个实时游戏实例难以发挥大量并行采样的优势，因此优先 SAC、用 TD3 作替代对照。这是依据样本复用特性作出的选择，不是 FH5 上的算法胜率结论。[SB3 SAC](https://stable-baselines3.readthedocs.io/en/master/modules/sac.html)、[算法与样本复用](https://spinningup.openai.com/en/latest/spinningup/rl_intro2.html)

Residual RL 把基础反馈控制与学习修正相加，在原论文中用于机器人任务；将它应用于 FH5 是本项目的实验假设，不是论文已验证的结果。[原论文](https://arxiv.org/abs/1812.03201)

## 第一阶段：把游戏接成可靠环境

建议模块与数据流：

```text
FH5 Data Out → 时间戳对齐的车辆状态 → 路线定位与前方航点
                                        ↓
                               基础控制器 / 学习策略
                                        ↓
                             限幅、延迟记录、虚拟手柄 → FH5

画面 → 比赛阶段 / 漏检查点 / 结束画面检测 → episode 管理
所有输入、动作、控制权、失败原因 → 录制与离线回放
```

Data Out 提供车辆状态，路线和可驾驶边界仍需自己建立。官方 Motorsport 协议不应直接当成 FH5 的字节布局；首轮抓包要核对长度、偏移、单位和符号。连接与字段依据详见 [FH5 接口调研](fh5-environment-research.md)。

首个工程任务不是开始长时间训练，而是完成一次接口验收：

1. 确认游戏版本 / 平台、目标赛事已解锁；选定一辆易控的 B/A 级车并固定调校、视角、辅助设置。
2. 接收原始 UDP 包；人工停车、加速、转向，验证速度、位置、朝向、油门刹车、转向符号。记录接收间隔分布、丢包和暂停行为。
3. 虚拟手柄在低速短段输出小幅转向和踏板；确认游戏接收、失焦行为、死区、速度相关的转向响应，以及退出/接管时解除动作。
4. 连续录制至少 10 分钟，区分接收时间、游戏时间、命令发送时间和推定的游戏响应时间。发送时间可直接记录，精确生效时间通常不可直接获得；用遥测/画面响应估计延迟，说明时钟对齐与估计方法，报告中位数与 p95，而非只报平均 FPS。
5. 做带状态确认的菜单重开流程，测 20 次重开成功率和耗时。若仍需频繁人工解卡，优先修环境或保留人工重开作短实验，不运行整夜无人训练。

FH5 的公开遥测/输入链路不能直接提供研究仿真器那样的 `step(1)`、任意状态传送和快进接口。评估未找到可直接采用的官方 FH5 Gym 环境；工程计划按一个实时实例和菜单重开计算。`Gymnasium` 可以统一 API，但包装 API 不会暂停游戏的物理时间。[Gymnasium Env](https://gymnasium.farama.org/api/env/)

控制循环必须持续运行，不能在一次梯度更新时让游戏无记录地继续前进。初版可选“驾驶采样一批 → 确认暂停/结束 → 训练一批 → 再采样”；后续使用独立采集与训练进程。真实延迟和前几步动作纳入状态；策略更新采用完整快照，记录版本。[TMRL](https://github.com/trackmania-rl/tmrl) 可借鉴这种实时采集训练架构，但它不是现成的 FH5 接口。

## 第二阶段：先得到可完赛的基线

人工录制一次或多次完整干净路线，保留世界坐标、朝向、速度、动作与时间；用空间弧长重采样并检查跳点。人工实际轨迹只是一条参考线，不等于道路中心线或最优赛车线。

每次控制读取车辆当前位置，先在上一次路线索引附近匹配，再计算横向偏差、航向误差和前方若干米航点，避免相邻道路、立交桥或闭合起终点导致误匹配。不能按原录制时间机械重放方向盘。

横向可先用随速度调整前视距离的 Pure Pursuit 或 Stanley；纵向用保守目标速度 + PI/PID。先从低速开始，标定“虚拟手柄量 → 实际转向响应”，并用曲率和制动距离让降速发生在弯前。简单几何公式不包含 FH5 的完整轮胎与手柄模型，高速能力必须实测。

参考项目报告的 Pure Pursuit 失败针对单组未调优参数，并不直接否定这里的已知路线、低速起步和速度相关标定方案；但它提醒我们必须检查转向增益与前视距离，而不能套公式就假定能完赛。详见 [相关审计](reference-project-audit.md#pure-pursuit-失败案例的适用范围)。

训练场景尽量固定天气、车辆、路面和对手干扰；可在游戏里验证适合的自建赛事设置。官方说明 EventLab 提供时间/天气编辑能力，但特定菜单和比赛设置仍以本机为准。[EventLab 2.0](https://forza.net/news/forza-horizon-5-horizon-creatives)

从 30–60 秒短段、连续弯道推进到较长路段，再到全程。**分段不意味着可以调用任意位置 reset**：要有实际可到达的赛事起点、经过验证的游戏内流程，或用基线先驶入目标路段。回溯/传送时结束当前训练片段，不能把位置跳变当成普通经验。

首个验收建议：连续 3 次完整跑完歌利亚，无人工方向盘/踏板接管、无倒带，游戏确认所有检查点并结束；固定辅助设置，关闭自动转向/自动刹车以清楚归因，ABS/TCS 可固定保留并报告。若测试在自建事件完成，应标为自建事件，不能写成已完成原版赛事。

碰撞避让是额外能力。仅有本车遥测和静态路线，不能感知前方其他车辆；含对手/交通的验收需补充视觉或另列失败因素。第一轮最好减少这类干扰，先验证沿路驾驶。

## 第三阶段：设计可解释的 RL 实验

建议 observation 使用低维、归一化的局部量：

- 车速、横向速度或侧滑、横摆角速度、必要的轮胎滑移。
- 相对路线的横向距离、航向误差、车体坐标系中的前方航点 / 曲率。
- 参考速度、基础控制器输出、过去动作、实际时间间隔；必要时加入基础控制器积分状态。

位置用于构造路线相对量，而不是只把世界坐标交给网络。这样更容易检查哪里错了，也减少对绝对地点的机械记忆；单条已知路线的成功依然只能说明已知路线性能。

第一个实验固定横向控制，RL 选择目标速度修正。第二个实验采用有界修正：

```text
最终动作 = 限幅(基础控制动作 + 允许的修正幅度 × 学习策略输出)
```

记录策略原始输出、修正量、限幅后的命令和可观测的实际响应。训练 critic 的动作定义必须与环境一致：若 Gym action 定义为归一化 residual，critic/replay 仍使用该 residual，最终限幅手柄量另行记录，不能拿后者直接替换前者。不能把未执行的原始动作标成最终执行动作。额外接管、滤波和控制器内部状态也要明确处理。

奖励初稿应围绕合法前进：沿参考路线的进度增量，扣除偏离、抖动与耗时，给予过关/完赛奖励，对漏检查点或持续失控终止。权重通过短段实验调整，避免提前撞毁比继续驾驶更划算。

不能用总行驶距离直接表示赛事进度。绕圈、倒车、走错路、穿越近邻道路、重置和地图投影跳跃均可能欺骗朴素奖励。限定路线匹配窗口、合理速度下的进度增量以及按序通过的检查点/门；最终以游戏认可的结束状态复核。停车惩罚也需跳过倒计时、暂停与载入。

实际失败与外部时间限制要区分；被菜单重开、断流或观察失效截断的片段，不应跨越重置拼接。没有有效末状态的数据段先剔除/单独处理，而不是盲目 bootstrap。[Gymnasium 时间截断说明](https://gymnasium.farama.org/main/tutorials/handling_time_limits/)

有了人工或基线驾驶记录，可做 BC 预训练、示范回放采样或额外 BC loss；这些是不同机制。把示范塞进 replay buffer 不会自动完成 BC，直接加载不同策略的权重也不等于正确 warm start。首轮无需同时实现全部方法。

## 时间和实验预算

以下是单个实时游戏实例的算术下限，**不是收敛预测**。Hz 指真实新决策频率，不是游戏 FPS 或重复画面计数。

| 决策数 | 10 Hz 有效驾驶时间 | 20 Hz 有效驾驶时间 |
|---|---:|---:|
| 10 万 | 2.78 小时 | 1.39 小时 |
| 100 万 | 27.78 小时 | 13.89 小时 |
| 1000 万 | 277.78 小时 | 138.89 小时 |

基础关系：有效采样小时 = 决策数 / (Hz × 3600)。若平均一次驾驶 30 秒、重开占 10 秒，重开本身就把总时间乘以约 1.33；还要计入失败诊断、评估、更新、休息与游戏占用电脑的时间。提高决策频率会增加相邻样本相关性，不能据此保证同比提高学习速度。

长赛道尤其需要稳定性。纯示意地，若一圈分成 50 个相互独立且每段成功率 99% 的段，整圈成功率仍只有约 60.5%。实际失败并不独立，此计算只说明为何短段表现好不等于全程可靠。

假期排期建议按验收门槛推进：

| 里程碑 | 产物 | 继续投入条件 |
|---|---|---|
| 接口验证 | 硬件/延迟日志、录制、控制、重开报告 | 采样与动作可信，重开足够稳定 |
| 基线短段 | 参考路线、低速闭环、失败回放 | 连续弯道通过且无隐藏人工接管 |
| 基线全程 | 完赛日志与录像 | 连续多次游戏确认完赛 |
| 首轮 RL | 相同短段下的 SAC 与基线对照 | 能解释收益或失败，并记录实际采样成本 |
| 全程 RL / 视觉 | 长赛道评估或感知替换 | 前面仍有充足时间且收益值得继续 |

若假期只有一周，应优先保住接口和基线完赛，把 RL 改善短段速度作为进阶成果；不能承诺一周内从零像素 RL 学会整圈。未测接口前，不给训练完成日期或固定成功概率。

## 如何判断实验有没有价值

保留同车、同调校、同辅助设置和相近场景的基线对照。首先报告完赛率、检查点遗漏、人工接管、失败位置和总交互小时；再报告成功回合的时间分布，不能只挑最快的一次。

首轮至少比较基础控制、RL 学速度、residual RL；若时间允许，加 BC-only 或全控制 SAC 对照。探索关闭后做评估，区分训练种子与重复评估次数；能负担时训练多个种子，不能把单次成功当统计结论。[SB3 实验与评估建议](https://stable-baselines3.readthedocs.io/en/master/guide/rl_tips.html)

有路线、有遥测的完赛是有效的导航控制成果。若以后追求仅画面驾驶，可让视觉网络预测目前由地图/遥测计算的几何量，再替换感知输入、保留经过验证的控制接口。训练时是否使用遥测与部署时是否使用遥测须分别写清楚。

下一项具体工作是 FH5 接口验证：UDP 录制器、虚拟手柄小幅控制、延迟测量、比赛重开和结束识别。它同时回答能否可靠采样、能否驱动和能否长期训练，是算法实现之前最有价值的一步。

## 补充：路线泛化与 AI 对手（2026-09-28）

用户进一步关心参考项目能否处理交通车/竞赛对手，以及本项目是否只能开固定赛道。这里把路线泛化与动态交互分开评估；它们是两条可独立推进的研究方向。本节为可选扩展，不把首次完赛目标改成必须赢得比赛。

### 参考项目实际证明了什么

驾驶源码根据实时画面与本车状态预测局部航点，不加载固定路线坐标表，也不按录制时间重放动作。它在架构上具有跨道路使用的可能性，但约 75% 评测路段出现在训练录制中，作者明确把该实验定位为跨车辆测试。它也没有独立的目的地/转弯指令和全局导航接口；在岔路口，局部道路形状不足以确定应走哪条路线，画面中的赛车线等提示可能提供路线信息。[驾驶源码](https://github.com/Ayin1412/ForzaHorizon6-VisionAI/blob/main/scripts/drive.py)、[README 局限性](https://github.com/Ayin1412/ForzaHorizon6-VisionAI#-limitations)

README 允许从自由漫游或比赛启动，但公开报告没有明确的车流配置、碰撞率、超车成功率或对手竞速评估。模型没有显式对手检测/跟踪和交互规划接口。图像中出现车辆仍可能影响其预测航点和速度，因此不能断言绝不会避让；合理结论是“尚未证明可靠处理交通和对手”。详见 [追加源码审计](reference-project-audit.md)。

### 已知地图仍然可以支持竞争

原方案录制的是参考轨迹，不是完整道路地图。若要绕车，需要再获得左右可行驶边界、检查点门和局部路面信息；这些可通过标注或视觉估计逐步补全，不能从一条录制线凭空推导出真实道路宽度。

建议保留全局路线，并把局部目标改为在合法走廊内选择路径：前车挡住参考线时，判断减速跟车还是在确认有空间时绕行，通过后再平滑返回。路线跟踪器持续处理转向与速度执行。固定路线的奖励也要调整，不能把一切离开参考线的动作都判为失败，否则会压制合理超车。

对手的位置与速度不在所核查的 FH5 Data Out 车辆字段中，需要额外感知。第一版可从画面检测与跨帧跟踪获得相对方位、接近趋势、距离估计及置信度。检测框不等于精确三维位置；视角、坡道、车型和遮挡都会影响估距。前视相机看不见的侧后区域不能默认为畅通。[FH5 遥测字段](https://github.com/csutorasa/go-forza-telemetry/blob/v1.2.0/v2.go)

推荐扩展后的结构为：

```text
本车遥测 + 已知道路/检查点 → 全局路线与当前进度
游戏画面 → 车辆检测、跟踪、相对运动和不确定性
两者 → 局部规划 / RL 决策 → 目标速度与局部路径 → 跟踪控制
```

### 对手模式的 RL 设计与投入判断

若对手是游戏内置且配置固定的 AI，只训练本车即可，不必先做自博弈或训练多个智能体。对手是环境的一部分；本车视角有遮挡与未知信息，观测需要历史信息，必要时研究循环策略。增加多个游戏 AI 不等于同时训练同样数量的神经网络。

RL 初期可以学习目标速度和有界横向目标，让局部规划器处理轨迹平滑、道路边界与可观测的碰撞风险。随后再比较直接动作策略。奖励兼顾合法进度、接触风险、完赛与时间；只奖励名次变化可能诱导不理想行为。碰撞标签也需核验，急减速只能作为代理信号。

建议按以下门槛推进，人数/起点/难度是否可调以实际赛事为准：

| 阶段 | 目标 | 关键新增能力 |
|---|---|---|
| 已知路线、空场 | 稳定完赛 | 地图定位、车辆控制 |
| 已知路线、有对手 | 保守跟车并完赛 | 检测跟踪、距离判断、减速避碰 |
| 已知路线、主动竞争 | 稳定超车，减少接触 | 局部轨迹选择、侧方观察、交互策略 |
| 陌生路线、有对手 | 跨路线竞速 | 道路感知、路线意图、分布外验证 |

起跑车群密集、并排行驶和被撞后的恢复须单独测试。能在车群远去后完成比赛，与能稳定近距离竞争是不同结果，应分别报告。评价新增超车成功率、接触次数、名次与跟车等待时间，同时保留原来的完赛率与漏点指标。

已有竞速 RL 研究证明这类能力可以学到，但不能直接外推本项目成本。例如 2025 年的 GT7 视觉竞速研究使用循环 actor 和可读取额外全局状态的训练 critic；我们没有等价的 FH5 对手状态接口。[原论文](https://arxiv.org/abs/2504.09021)

本机仍适合轻量车辆检测、跟踪和小型策略的实验；实际闭环延迟需在游戏同时运行时测量。相较空场完赛，主要新增成本是感知数据、交互场景覆盖、失败恢复和评估，而不是简单增大网络。合理的下一扩展目标是“固定歌利亚路线、固定 AI 难度、有对手仍可靠完赛”，之后再研究夺冠。

为保持扩展性，控制器输入使用局部航点、曲率、边界和对手相对量，不硬编码歌利亚的路段编号或固定动作。歌利亚可以作为第一份地图；换地图后是否无需重训，则通过留出的其他路线验证。
