# 采集优先的 BC 训练调度（T36 / #38）

`collection-bc-train` 在固定数值快照上运行现有 Δt BC。它只读取指定采集进程和主机资源，不启动游戏、停止采集或取得驾驶控制权。软件调度已具备；真实 4K 游戏/训练共存预算尚未验证，示例阈值是候选配置。

```powershell
uv run --locked fh5 collection-bc-train --config configs/collection-learning.example.json --output runs/scheduled-candidate-001
```

将示例中的路径和 SHA-256 替换为实际值：`training_config` 使用现有 Temporal BC 配置；`collector_bundle` 指向 `collection-prepare` 生成的独立环境，哈希绑定其中 `frozen.json`。路径相对调度配置文件。输出必须是新目录，并位于输入数据集和采集环境之外。工作区后续修改不会改变已经封存的数据清单。

## 调度规则

- CPU 训练使用配置的 1–2 个 Torch 计算线程，指定采集进程健康时可以并行。检查进程身份、版本核验、心跳和采样时间、图像年龄、归档积压及新增丢弃。图像年龄取采样时的年龄；心跳发布延迟另行检查，不能把每秒发布一次状态误算成图像管线变慢。
- CUDA 采用交错基线：等待指定采集进程退出且正常释放/封存后，再按设备显存与利用率预算运行。不把暂停菜单或陈旧状态当作可用 GPU 时隙。其他 GPU 程序仍可能消耗资源；此机制不提供设备独占，也不证明实际游戏时效。
- 初始化、每次优化器更新、冻结和逐观测预测之间检查预算。压力出现时停止派发新工作，将模型/优化器张量移到 CPU，释放可回收的 CUDA 缓存；连续两次健康观测后恢复。CPU 张量仍保留，以便同一次运行继续相同优化器和随机序列。
- 本进程内存或磁盘余量越界、采集失败、单次工作超时、总时长或连续等待超限时停止。调度是协作式的：正在执行的单个 Torch 操作不能由本模块强行抢占，超时在操作返回后记录并阻止下一步。它不能替代 #36 的独立动作到期机制。
- 资源查询在学习端进行并按 `poll_interval_s` 限频；采集热路径只更新现有状态字段。状态样本最多 16 KiB，保留最近 1000 条及累计压力计数，超出的诊断条数可见。CPU 模式不调用 NVIDIA 资源查询。

## 结果与停止

`schedule.json` 记录等待、压力原因、已完成更新数、最长工作单元、输入配置和候选哈希。`requested-training.json` 保留原配置字节，`training.json` 固定解析后的数据路径。完整训练和重载验证结束后，才把 `.candidate` 发布为 `candidate/`，其中仍是标准 BC 模型和联动画面报告。停止时不发布候选，可能留下 `.candidate` 诊断文件；这不是可续训检查点，完整跨进程续训仍由 #13 实现。

在输出目录创建 `stop.request` 或在前台按 Ctrl+C 可停止；工作单元返回后响应并保留诊断。完成返回码为 0，受预算或停止请求限制返回码为 2；输入损坏等错误保存诊断后报告异常。原始采集与输入数据不会因此删除或更改。

旧采集环境缺少 `last_poll_ns`、`latest_image_source_ns` 或 session 绑定时不能凭旧状态推断资源健康；应重新准备新的采集环境，保留旧录制。旧的 `temporal-train` 是不带采集协调的离线入口，采集期间应使用本入口。

已用合成输入验证压力暂停后与同种子普通训练预测一致；独立合成采集进程和真实 Windows 只读资源计数完成并行原型。CUDA 张量迁移与真实游戏负载仍需后续实测，不将 CPU 软件验证写成 GPU 性能结论。
